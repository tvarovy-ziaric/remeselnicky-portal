# Phone verification security boundary (R0-011)

## Scope and authority

Phone verification is an authenticated, server-authoritative account command.
It does not grant marketplace capabilities by itself; later customer/provider
commands must require both email and phone verification under D02. A suspended
or deactivated account cannot send or consume a challenge, including from an
already-open browser session.

`auth_credentials.normalized_phone` is private contact data. It is populated
only in the same database transaction that consumes a valid OTP, and
`phone_verified_at` is generated by PostgreSQL. A candidate phone remains on
the short-lived challenge and does not replace an already verified contact
unless verification succeeds.

## Secret lifecycle

- The API accepts canonical international numbers (E.164) and normalizes only
  harmless presentation separators and the `00` international prefix.
- OTPs contain six decimal digits generated by Node's cryptographic RNG.
- Each challenge has a new 128-bit random salt. PostgreSQL stores only the salt
  and an HMAC-SHA-256 digest made with a 32+ byte server-side pepper and domain
  separation; the plaintext OTP is never passed to persistence.
- The current runtime derives the pepper boundary from the server-only session
  secret. Rotating that secret intentionally invalidates outstanding OTPs.
- Plaintext OTPs cross only the narrow delivery-provider port. Provider errors
  are replaced with a generic error, and the issued challenge is invalidated.
  Ordinary logs, errors, traces and database records must never contain an OTP.
- Challenges expire, are single-use, and are superseded when a new challenge
  is issued. Verification attempts increment atomically; the final incorrect
  attempt invalidates the challenge.

## Abuse controls and privacy

Send/resend consumes shared PostgreSQL rate buckets for account, normalized
phone and IP. Verify consumes account and IP buckets in addition to the atomic
per-challenge attempt limit. Bucket keys are HMAC digests, not raw phone/IP
values. IP limits are deliberately looser than account limits so shared/NAT IPs
do not become identity or reputation verdicts. Responses do not expose whether
a challenge was absent, superseded, expired, exhausted, already consumed or
contained a wrong code.

The phone-verification provider receives only the normalized destination and
the OTP needed for delivery. It receives no email, profile, role, account state
or marketplace content. Selecting a real production provider, processor terms,
region and credentials remains an external-vendor HUMAN GATE under D27/D30.

## Provider modes

`PhoneVerificationDeliveryPort` is provider-neutral. Tests and synthetic
staging harnesses can inject `createSyntheticPhoneVerificationDelivery`, which
accepts only `development`, `test` or `staging` at the type boundary and sends
the secret directly to a supplied non-logging sink. The normal runtime does not
install this adapter. Without an explicitly configured delivery provider, the
send endpoint returns a generic `503` and creates no challenge; production
therefore fails closed rather than pretending delivery succeeded.

## Configuration defaults

- OTP lifetime: 10 minutes (`PHONE_OTP_TTL_SECONDS`)
- Challenge attempt limit: 5 (`PHONE_OTP_MAX_ATTEMPTS`)
- Send/resend account and phone limit: 3 per 15 minutes
  (`PHONE_OTP_RESEND_LIMIT`, `PHONE_OTP_WINDOW_SECONDS`)
- Verify account limit: 10 per 15 minutes (`PHONE_OTP_VERIFY_LIMIT`)
- IP buckets use four times the corresponding account limit.

All bounds are validated at startup. API responses use `Cache-Control:
no-store`, cookie-authenticated state changes require CSRF protection, and
contact data is not returned by the verification endpoints.
