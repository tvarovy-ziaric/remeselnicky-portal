# Admin privileged access and MFA foundation

Status: R0-012 implementation baseline. Locked references: D23, D26 and D30.

## Security boundary

The ordinary `User` account remains the identity root. `ADMIN` and
`SUPER_ADMIN` are separate, revocable server-side grants; they are never read
from registration, login or another client payload. A normal authenticated
session has no admin authority. Every `/v1/admin/*` handler first reloads the
active account and then requires an unexpired MFA-backed privileged session and
the concrete capability for the command. Route naming, navigation visibility
and a frontend role flag are not authorization boundaries.

`ADMIN` receives the bounded operational capability set. It cannot manage
roles or read capability-gated sensitive fields. `SUPER_ADMIN` additionally
receives `admin.roles.manage` and `admin.sensitive.read`. Feature tickets must
still define object, field and action policies; `admin.access` is not a blanket
"see or mutate everything" permission.

There is deliberately no generic admin CRUD endpoint, arbitrary status patch,
SQL console, user impersonation or password-setting facility.

## MFA and session lifecycle

MFA is a provider-neutral port supporting TOTP and WebAuthn factors. PostgreSQL
stores only bounded, namespaced opaque provider credential/state references.
Unstructured secret-like strings are rejected at both service and database
boundaries. TOTP seeds, WebAuthn
private material and recovery codes must remain in the selected provider or a
dedicated secrets system and must never enter portal tables, sessions, API
responses or logs.

The challenge returned to the browser has 256 bits of randomness. Only its
SHA-256 digest is persisted. Each verification attempt atomically claims a
challenge before calling the provider, so a failed, concurrent or replayed
attempt cannot reuse it. The API also consumes the shared database rate bucket
using two keyed digests: a strict account bucket that survives IP rotation and
a separate, looser IP ceiling that does not punish a legitimate shared/NAT IP
as if it were an identity. Provider or rate-store failure denies access.

Before successful verification can grant privilege, the route regenerates and
persists the normal session ID. Verification atomically consumes the claimed
challenge and binds a short-lived privileged session only to that fresh,
revocable base-session digest; the pre-MFA digest is no longer usable.
The default privileged lifetime is 30 minutes. Role changes require MFA no
older than five minutes. Suspension, base-session revocation, factor revocation
or removal of all active privileged roles makes authorization fail immediately.
All admin responses use `Cache-Control: no-store`; the projection contains only
roles, capabilities and the MFA timestamp.

## Role-change provenance

Only an active `SUPER_ADMIN` with the role-management capability and recent MFA
can invoke the internal dedicated role command. The service denies every
self-role change. Persistence rechecks the actor's live base session,
privileged-session expiry and MFA age, active factor, active account and live
superadmin grant while holding locks inside the mutation transaction. It then
changes one named role, revokes the target's existing
privileged sessions and appends `admin_role_change_events` in the same
transaction. Those event rows reject update/delete and are ready to feed the
unified R0-024 audit facility.

## Production bootstrap gate

The repository intentionally does not select an MFA vendor, create a paid
account, accept production credentials or silently grant the first superadmin.
Production wiring remains fail-closed unless an `AdminMfaProvider` adapter is
explicitly supplied. Selecting/authorizing that external provider and
credential flow, enrolling the first production factor, and granting the first
`BOOTSTRAP` superadmin are HUMAN GATE items. A dedicated, one-shot audited
operations command must perform bootstrap after that decision; application
routes must never expose `grant_source=BOOTSTRAP`.

Before D30 go/no-go, evidence must show a real provider-backed TOTP or WebAuthn
enrollment, challenge/replay/rate tests, privileged-session expiry, role-change
audit ingestion and emergency recovery owned by named operators. No recovery
code is generated by this foundation because securely issuing and custodying
one is provider and policy dependent.
